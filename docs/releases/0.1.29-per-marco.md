# Aggiornamento Devsync per Marco

Da Claudio a Marco Deias · 13 novembre 2026 · Release 0.1.29

Ciao Marco, abbiamo completato un primo intervento sulle proposte che ci hai mandato. La 0.1.29 aggiunge commenti nelle task, tag, creazione progetti via MCP e filtri per interrogare l’audit. Include anche le correzioni e le funzioni pubblicate nella 0.1.28, riepilogate sotto. Il riferimento per aggiornare la tua istanza è `caporro/devsync:0.1.29`.

Ci fermiamo a questo insieme di modifiche. Le altre proposte restano da valutare se emergerà un limite concreto nell’uso; non sono impegni di sviluppo. La pubblicazione della release non aggiorna automaticamente la tua istanza.

## Novità della 0.1.29

**Commenti nelle task.** Puoi aggiungere una risposta dalla UI, via MCP con `append_task_comment` o via REST. Ogni commento ha autore, data UTC e ID assegnati dal server ed è conservato nello stesso Markdown della task, dopo la descrizione. Non servono file separati. Le risposte precedenti restano conservate quando si modifica la descrizione; questo incremento permette solo l’aggiunta di commenti.

Gli inserimenti concorrenti sono serializzati nello stesso processo e non richiedono `expectedRevision`. Le normali modifiche della task continuano a richiedere la revisione corrente. Usiamo un solo processo scrittore per vault: processi HTTP e stdio separati non condividono il lock.

**Tag delle task.** Il campo `tags` è disponibile in creazione e modifica da UI, MCP, REST e Assistant. Le etichette sono nel frontmatter Markdown e possono sostituire le convenzioni basate sui prefissi dei titoli. Lista task e Kanban offrono un filtro per tag. Le etichette distinguono maiuscole e minuscole; omettere `tags` conserva quelli esistenti, mentre `[]` li rimuove.

**Progetti via MCP.** Il nuovo `create_project` crea la struttura iniziale con la stessa operazione del REST. Accetta `name` e, facoltativamente, `slug`, `owner`, `status`, `tags` e `agentName`. L’ID cartella deriva da `slug` o `name`; il nome visualizzato segue l’ID cartella. Un progetto già presente restituisce 409 e non viene sovrascritto.

**Audit filtrabile.** Il nuovo tool `list_system_log` e il REST accettano `actor`, `authenticatedBy`, `action` e `limit`. La UI ha filtri separati per autore e utente autenticato. I filtri si combinano con AND e precedono il limite dei risultati. I vecchi eventi senza identità autenticata registrata non vengono completati con dati dedotti.

## Esempi per gli agenti

I seguenti sono nomi di tool MCP e relativi argomenti; sostituisci progetto e path con quelli restituiti dalla tua istanza.

**Aggiungere una risposta con `append_task_comment`**

```json
{
  "projectId": "inbox",
  "path": "tasks/consegna.md",
  "content": "Verifica completata. Possiamo chiudere.",
  "agentName": "Custode"
}
```

Equivalente REST: `POST /api/projects/inbox/tasks/comments?path=tasks/consegna.md`, con `content` e l’eventuale `agentName` nel JSON e l’autenticazione già configurata. MCP restituisce `{comment, path, revision}`; REST aggiunge la task aggiornata in `task`. `read_task` restituisce `content` completo, `descriptionContent` senza discussione e l’array `comments`.

**Creare una task etichettata con `create_task`**

```json
{
  "projectId": "inbox",
  "title": "Verificare la consegna",
  "tags": ["handoff", "audit"],
  "agentName": "Coordinatore"
}
```

Per recuperarla: `list_tasks({"projectId":"inbox","tag":"handoff"})`. Per cambiare i tag usa `update_task` con path, `tags` e `expectedRevision` dell’ultima lettura.

**Creare un progetto con `create_project`**

```json
{
  "name": "Agent Hub",
  "slug": "agent-hub",
  "tags": ["shared"],
  "agentName": "Coordinatore"
}
```

**Interrogare l’audit con `list_system_log`**

```json
{
  "actor": "Custode",
  "authenticatedBy": "marco@example.com",
  "limit": 50
}
```

L’email è un esempio: usa l’identità realmente registrata dalla tua autenticazione. Con il token REST condiviso, `authenticatedBy` vale `api-token`. Il nome dell’agente resta in `actor`.

## Già risolto nella 0.1.28 e incluso nella 0.1.29

- Titoli con parentesi quadre e completamento: la migrazione comprende le etichette Markdown con escape e conserva la spunta presente nell’indice originale.
- Nomi file lunghi: le nuove scritture conservano l’estensione. Per i vecchi file troncati esiste una procedura esplicita di anteprima e riparazione con backup; l’aggiornamento non li rinomina automaticamente.
- `append_log` via MCP: i diari possono stare nei log invece che nelle task. Le voci lunghe diventano risorse Markdown collegate.
- `list_tasks` espone autore originale e ultimo editor, filtri combinabili (`done`, `status`, `owner`, `createdBy`, `overdue`, `updatedSince`), risposte compatte e paginazione `limit`/`cursor`. La 0.1.29 aggiunge il filtro `tag`.
- `agentName` opzionale su MCP e REST: ogni chiamata può indicare il proprio agente anche se più agenti condividono client e credenziali. Se manca o è vuoto, l’autore è l’utente autenticato. L’audit conserva sempre l’identità autenticata separatamente. Il nome è dichiarato e non attribuisce permessi.
- Le modifiche preservano il creatore originale. I campi grezzi inviati dal client, come `createdBy`, `author` o `authenticatedBy`, non sostituiscono l’attribuzione del server. `expectedRevision` protegge le modifiche da una lettura ormai superata.

## Aggiornamento e dati esistenti

Se sei già sulla 0.1.28, aggiorna alla nuova immagine mantenendo volume dati e configurazione del vault, poi riconnetti il client MCP per aggiornare i tool disponibili. Commenti e tag non richiedono una nuova migrazione. Le configurazioni Assistant con una lista di tool personalizzata devono aggiungere `append_task_comment` per usarlo.

Se arrivi dalla 0.1.24 o da una versione precedente alla migrazione delle task, segui prima le note di aggiornamento della 0.1.28: ferma gli scrittori e conserva un backup dell’intera directory dati fuori dal volume attivo. Per i nomi file troncati, i comandi disponibili nell’immagine sono:

```sh
node scripts/migrate-tasks.mjs --repair-filenames --dry-run
node scripts/migrate-tasks.mjs --repair-filenames
```

Eseguili con lo stesso volume e le stesse variabili del vault. Il primo comando mostra l’anteprima; il secondo applica riparazione e migrazione. Gli originali vengono conservati in `tasks/.filename-repair/` e `tasks/.migration-v2/`. Una spunta già persa da vecchie versioni è recuperabile solo se esiste ancora un indice originale o un backup che la contiene.

Per modificare una task, leggila e passa la sua revisione come `expectedRevision`. Un commento cambia la revisione: rileggi prima di una successiva modifica. Se una pagina di `list_tasks` restituisce 409, riparti senza cursore perché il risultato è cambiato. I nuovi commenti non richiedono una revisione dal client; una scrittura esterna concorrente può comunque produrre 409.

## Cosa rimane fuori da questo intervento

Restano rinviati chiusura multipla, relazioni `supersedes`, ricorrenze, archivio, webhook esterni, notifiche di scadenza e rinomina generale dei file task. Per le scadenze è già utilizzabile `overdue` via API e MCP; non aggiungiamo ora una vista dedicata nella UI. Token personali REST e accessi esterni con scope richiederebbero una decisione separata. Planning e Gantt restano rimossi; i vecchi file sono conservati.

Le verifiche automatiche sulle funzionalità comprendono 110 test backend, 5 frontend, lint e build. Non abbiamo effettuato una verifica interattiva sulla tua istanza.
