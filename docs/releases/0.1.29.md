# 0.1.29 — release and upgrade notes

Release tag: `v0.1.29`. Docker image: `caporro/devsync:0.1.29` (`linux/amd64` and `linux/arm64`). The tag pipeline publishes the image after validation.

## Changes since v0.1.28

- Append-only task comments in the task's existing Markdown file, with server-assigned ID, author and UTC date. UI, REST, MCP and the internal Assistant share the same operation. Description edits preserve existing comments. Appends are serialized per project within the process and do not require a client `expectedRevision`.
- Task tags stored in Markdown frontmatter, supported by UI, REST, MCP and Assistant tools. Task lists and Kanban can filter by one exact tag. Omitted tags are preserved on edits; `[]` clears them.
- MCP `create_project`, backed by the same filesystem operation as REST. Duplicate and concurrent creation attempts cannot overwrite an existing project.
- Audit queries over MCP (`list_system_log`), REST and UI, with separate operational-author (`actor`) and authenticated-user (`authenticatedBy`) filters. API filters combine with action using AND and are applied before the result limit.

## Upgrade and client compatibility

From 0.1.28, keep the existing data mount and vault configuration and update the application/image to 0.1.29. Comments and tags require no additional migration. Refresh the MCP connection/tool definitions to discover the new tools and parameters. Custom Assistant tool lists must explicitly include `append_task_comment` to enable comments.

If upgrading from an earlier version or recovering tasks whose filenames lost `.md`, follow the [0.1.28 maintenance and backup procedure](0.1.28.md#upgrade-procedure) before normal writers resume. New writes preserve extensions; recovering historical filenames remains an explicit maintenance operation.

- `read_task` and the REST task-content endpoint return the full `content`, separate `descriptionContent`, structured `comments` and current `revision`. Compact lists omit description/comment bodies.
- MCP/Assistant comment appends return `{comment, path, revision}`. REST returns `{comment, path, revision, task}` with the full updated snapshot. A new comment changes the task revision; normal task edits still require the latest `expectedRevision`.
- Comments can be added, but existing comments cannot be edited or deleted through task/document update APIs. Direct filesystem edits remain authoritative; malformed reserved comment sections produce an explicit error.
- Concurrency protection is within one writer process per vault. Separate HTTP/stdio processes do not share the lock. An external write can still produce 409; reread before retrying.
- Optional per-call `agentName`, authenticated-identity audit retention, original creators and existing REST authentication rules retain their 0.1.28 behavior. No new agent registry or permissions are introduced.
- Historical audit events lacking `authenticatedBy` are not backfilled and do not match that filter. Actor/authenticated-user and tag comparisons are exact and case-sensitive.
