# 0.1.28 — release and upgrade notes

Release tag: `v0.1.28`. Docker image: `caporro/devsync:0.1.28` (`linux/amd64` and `linux/arm64`). The tag pipeline publishes the image after validation.

## Changes since the v0.1.27 tag

- Searchable Markdown documents with stable IDs, protected creation metadata, revision-checked publishing/editing and MCP document tools.
- Self-contained task files with six states, revision-checked writes, automatic legacy checklist migration and the global Kanban.
- Planning/Gantt removed; existing planning files remain on disk.
- Filename truncation preserves Markdown and other extensions, including collision suffixes. Escaped Markdown labels are supported when importing legacy checklists.
- Explicit preview/repair of old truncated task filenames, with source backups and collision-safe destinations.
- MCP `append_log`, including long-entry resources and the existing log automation event. Concurrent entries and segment rotation are serialized within the process.
- Task summaries expose creator/editor metadata. Project task lists support combined filters, compact/full responses and optional cursor pagination over HTTP and MCP.
- Optional per-call `agentName` on MCP and REST writes. A supplied name becomes the operational author; blank/omitted names use the authenticated user. Audit events always retain the server-derived `authenticatedBy` separately from `actor`.
- Compatible backend dependency security updates, plus maintenance scripts included in the production Docker image.

## Upgrade procedure

1. Stop HTTP/stdio writers and back up the entire mounted data directory, including the vault, auth configuration and system log. Keep that backup outside the live volume.
2. Install the new code/image without starting normal writers. Use the same data root, vault name and any legacy data-directory configuration as the server.
3. Preview historical filename repairs with `npm run migrate:tasks -- --repair-filenames --dry-run`. Inspect any skipped candidates.
4. Apply repairs and task migration with `npm run migrate:tasks -- --repair-filenames`. With no repair flag, `npm run migrate:tasks` keeps its original metadata-migration behavior.
5. Start normal writers after the command succeeds. Update clients that write tasks to read the current revision and send `expectedRevision`.

The Docker image includes the maintenance scripts and runs them directly with Node (npm is not installed in the production image). With the usual `/data` mount and vault environment, override the container command with:

```bash
node scripts/migrate-tasks.mjs --repair-filenames --dry-run
node scripts/migrate-tasks.mjs --repair-filenames
```

Search-index maintenance is available with `node scripts/reindex-documents.mjs`.

`--dry-run` with `--repair-filenames` only inspects files; it does not migrate metadata, rename legacy folders, initialize the search cache or create backup files. Repairs preserve original file bytes and README under `tasks/.filename-repair/`, plus a rename map. Metadata migration separately preserves originals under `tasks/.migration-v2/`. These local backups supplement the full pre-upgrade backup.

Task metadata migration otherwise runs when a project's tasks are first accessed, including through project listing. At startup, document indexing may already assign IDs to Markdown files. Migration preserves existing creation metadata and bodies; it imports old checkbox state, owner, deadline and order, then generates the task README. The old README is no longer writable task state. If a generated index already omitted malformed filenames, repair can recover missing checkbox/assignment data from its migration backup. It cannot infer data previously discarded without a surviving index or backup.

## Client compatibility

- Existing MCP `list_tasks({projectId})` returns an array of summaries. Existing HTTP project lists return `{items}`. Bodies remain excluded by default.
- `limit` or `cursor` opts into `{items, nextCursor}`. Repeat filters on subsequent pages. A 409 indicates a changed query/result snapshot: restart without the cursor.
- `createdBy` in client task creation input does not select authorship. Use optional `agentName` for declared attribution; the authenticated channel identity remains imposed server-side in the audit, and historical creators remain intact.
- REST authentication and token identity management retain their existing behavior. The agent name is a free label, with no separate credentials, registry or project permissions.
